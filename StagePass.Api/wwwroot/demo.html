How It Works

❌
The Naive Approach (Broken)
Read available count into C#. Check if available ≥ quantity. Issue a separate UPDATE. Under concurrent load, two requests both pass the check before either commits. Result: overselling.
✅
The Atomic Approach (StagePass)
Push the check and decrement into a single SQL statement. SQL Server serialises concurrent UPDATEs at the row level. The second request finds Available already reduced and affects 0 rows — rejected cleanly.
UPDATE TicketTypes SET Available = Available - @qty WHERE TicketTypeId = @id AND Available >= @qty AND PerformanceId IN ( SELECT PerformanceId FROM Performances WHERE Status = 'Upcoming' )
🔑
Idempotency
Each request carries a unique client-generated GUID. If a network retry re-sends the same key, the server returns the existing hold — never a duplicate. A UNIQUE index enforces this at the database level.
⏱
Hold Expiry
Unconfirmed holds expire after 5 minutes. A background worker restores inventory using an aggregated batch UPDATE — so expired tickets re-enter the available pool correctly even when multiple holds expire at once.
