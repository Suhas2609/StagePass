How the guarantee works

❌

The Naive Approach

Most systems read available count into memory, check it in code, then issue a separate UPDATE. Under concurrent load, two threads both read "1 remaining" before either commits. Both proceed. You oversell.

✅

The Atomic Approach

StagePass pushes the check and decrement into a single SQL statement. SQL Server serialises competing UPDATEs at the row level. The losing request finds zero rows affected and is rejected cleanly — with no partial state.

UPDATE TicketTypes SET Available = Available - @qty WHERE TicketTypeId = @id AND Available >= @qty AND PerformanceId IN ( SELECT PerformanceId FROM Performances WHERE Status = 'Upcoming' )
🔑

Idempotency

Each request carries a client-generated UUID. If a network retry re-sends the same request, the server returns the existing hold — never a duplicate. A UNIQUE index enforces this at the database level, even under race conditions.

🛡️

Database Constraints

SQL Server CHECK constraints prevent Available from going below 0 or above Capacity at the engine level. Even a bug in application logic cannot violate the invariant — the database itself refuses the write.

🔄

Controlled Concurrency

The demo uses a rolling pool — keeping exactly Pool Size requests active at any moment. As each resolves, the next fires immediately. This prevents browser socket exhaustion at high request counts and mirrors how real load testers like k6 work. The inventory guarantee holds regardless of pool size.
